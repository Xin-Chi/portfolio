Venom-Bot
LINE × Gemini 個人 AI 聊天機器人

Personal Project｜2026.6–2026.7（上線中，給多位朋友實測）
摘要
  • 獨立完成端到端開發與維運：架構設計、部署、上線後除錯、多人測試迭代，全程一人負責
  • 支援 7 種輸入格式（文字／貼圖／圖片／語音／影片／PDF／連結），共用同一套記憶與防呆邏輯
  • 反覆迭代人設 Prompt 設計，並對上線後的 bot 做過 Prompt Injection 資安自測
  • 遇到 4 個真實工程挑戰（免費方案休眠、跨平台格式限制不對稱、隱藏 bug、PDF 成本抓錯指標），全部靠實測數據而非猜測解決
專案概述

獨立設計並上線一個 LINE × Gemini 聊天機器人，後端以 FastAPI 自行開發、部署於 Render。 專案涵蓋機密保護、部署、上線後除錯，到多人測試後的穩定性修正，每個設計都以實測數據與真實 bug 驅動，而非紙上規劃。

除錯歷程
①免費方案的「休眠」問題，得自己接外部服務解決
Render 免費方案閒置 15 分鐘會自動休眠，冷啟動需約 60 秒——比 LINE 本身的回應時限還長， 使用者第一次傳訊息很可能完全等不到回覆，體驗上很像「機器人壞了」。解法是要有人定期從外部打進來保持清醒，但同樣得在免費額度內做到。 原本想用 GitHub Actions 排程，查了才發現每次執行最少算 1 分鐘，5–10 分鐘頻率一個月會燒掉約 4,320 分鐘，遠超 2,000 分鐘的免費額度，大約 14 天就會用罄。
✓改用 UptimeRobot，免費方案每 5 分鐘 ping 一次，額度用不完，完全不用人工介入確認，實現 0 成本
②朋友多人測試揪出的兩個隱藏 bug
一次朋友連續傳 30 張圖片，才發現訊息處理失敗時沒有妥善的容錯機制，會拖累整批訊息都收不到回覆。 同時也發現「呼叫太頻繁被 Gemini 暫時拒絕」的重試邏輯寫成全體共用，一人狂傳會連帶讓完全沒亂傳的其他人也已讀不回。
✓補上容錯機制讓單則失敗不影響其他訊息，並把限流狀態改成以每個使用者獨立計算。兩個問題都是靠朋友實測才浮現，不是事前能猜到的
③多模態輸入的「能傳」跟「能處理」常常對不上
LINE 允許使用者傳到 200MB 的檔案，但 Gemini 語音只吃 20MB、影片只吃 100MB，兩邊限制完全不對稱，得自己另外加一層防呆。 而且該用哪個指標（檔案大小／時長／頁數）才抓得住真正的成本，每種媒體類型還不一樣，得個別驗證才知道。
✓語音、影片改用 LINE 訊息自帶的時長判斷，三種媒體、三套各自驗證過的防呆標準
④PDF 用「檔案大小」限制成本，其實抓錯了指標
一開始以為檔案大小能有效限制 token 成本，實測後發現：一份僅 0.28MB、300 頁的純文字 PDF，要吃掉 160,168 tokens，單次就用掉每分鐘額度的 64%。 檔案大小跟頁數完全不成比例。
✓查明後發現Gemini處理pdf檔案是用頁數固定258 token計算。改用以 pypdf 實際算頁數把關（6 頁上限），才是真正抓得住成本的指標
這四個挑戰的共通點
光讀文件或憑直覺猜不到答案，得靠真實資料實測，甚至嚴謹的比較才找得到真相，而且結果常與一開始的假設完全相反。
功能設計亮點
結構化輸出一次呼叫完成回覆＋表情包判斷
用結構化輸出讓 Gemini 在同一次呼叫裡同時產生回覆文字與可選的表情包 ID，不需額外請求；表情包依Gemini判斷後設計即使情境符合,也只有 25% 機率真的附圖,增加訊息傳送的變化性。
人設語氣的迭代設計（Prompt Engineering）
初版人設「有點嗆」被朋友反饋太衝，兩輪調整成「禮貌有理、偶爾吐槽」；另外加上「提到作者要恭敬」的規則，上線後又發現模型會自己主動搬出作者當話題，再追加「不能主動提起」修正。每次調整都要重新測過說話模式、故意找碴、提到作者等情境，確認新語氣沒有意外副作用。
Prompt Injection 自我測試
對已上線 bot 實測多種常見手法（洩漏系統設定、指令覆蓋、突破字數限制、誘導亂編答案、角色扮演越獄），全數擋下；有被使用者逼迫透漏的內容也純屬虛構，非實際方法與技術。
